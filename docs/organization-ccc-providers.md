# Organization CCC provider rollout

Existing facilities and public signups default to the existing NHIA provider. The existing direct-API enabled setting and credentials still apply. Platform-created facilities can select OTAC, initially disabled, then configure it under Tenant Admin → expand facility → CCC integration.

## Deploy in order

1. Apply `supabase/migrations/20261010090000_organization_ccc_providers.sql`.
2. Deploy `tier-access` and `tenant-signup`, retaining the existing NHIA encryption key. OTAC secrets use the existing AES-GCM encryption implementation.
3. Update **every branch installation** before enabling OTAC for its organization. Older branch binaries can still call the old eligibility endpoint directly and do not honor this policy. Updated branches require cloud connectivity and centrally saved existing-provider credentials; local-only credentials are no longer sufficient for CCC generation.
4. Deploy the frontend. Configure each facility's own HPN, exact NHIA facility name and token. Enable only after all its branch installations are updated.

Saving a token checks its format, expiry and declared HPN. This is not signature verification or a successful NHIA connection test. NHIA authenticates the token on attendance generation; returned facility name, date, code and attendance ID are checked. No patient attendance is generated by saving settings.

## Attendance handling

CCC generation is an explicit action, not a member-field blur action. Only today's attendance can be generated. One successful or unresolved request per organization/member/card/date is retained across cloud and updated branch clients. Success is reused even if the token subsequently expires. A pending/unknown request blocks another request and provider switching.

After checking the actual outcome with NHIA, a platform administrator can reconcile a request older than five minutes in the recent-request panel. Record the confirmed attendance and ID, or evidence that NHIA created none. Timeout alone is not evidence of non-creation. Reconciliation is audited. There is no automatic fallback to another provider.

Tokens are never returned by the policy API. Facility users cannot edit provider settings. Branch requests use the branch sync credential and authenticated local actor identity; the cloud verifies organization membership and claims permissions.

## Rollback

Reconcile unresolved requests before switching a facility back to the existing provider. Retain the ledger and migration; do not delete attendance history or deploy older branch code while OTAC remains enabled. Disable CCC generation if upstream configuration is uncertain. CLAIM-it export settings are independent.

## Verification limits

Automated tests use synthetic tokens, mocked NHIA responses and an isolated PostgreSQL-compatible database. Production token authorization and actual NHIA attendance must be verified separately after deployment. Tokens previously shared in chat are not seeded into this implementation.
