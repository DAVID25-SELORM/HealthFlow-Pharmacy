# NeHFAMS first authorized test procedure (operator checklist)

Status: prepared, **not executed**. No NHIA request has been made by HealthFlow or by the people who prepared this document.
Source of the API contract: NHIA's "NeHFAMS HMIS Non-Biometric Authentication API" workbook and the "HFAMS - HMIS Vanilla" Postman collection.
Anything marked **[NHIA]**, **[CREDENTIALS]** or **[TEST MEMBER]** cannot be done without that item from NHIA. Do not guess it.

## 0. Rules for the whole session

- Use only the **test** origin `https://elig.nhia.gov.gh:5007`. Never configure or use `https://nehfams.nhia.gov.gh` (production) in this session.
- Never use a real patient or real member number. Use only members NHIA supplied for testing. **[TEST MEMBER]**
- Never paste credentials, tokens, full responses or member details into chat, tickets, source control, logs or screenshots. Keep evidence in a protected location, redacted.
- Do not call the Postman "HMIS DevTools" routes (`/api/devtools/genotac`, `/api/devtools/getotp`) from HealthFlow, and do not assume they exist in production. They are test-tool routes. If a 2FA OTAC is needed, obtain it through the procedure NHIA authorizes. **[NHIA]**
- Run against a **disposable HealthFlow test backend and database**, not the production project. Keep the existing legacy NHIA provider untouched.
- One attendance creation at a time. Never repeat a request whose outcome is uncertain.

## 1. Confirm environment and authorization **[NHIA]**

1. Get written confirmation from NHIA that the test origin, the test credentials and the listed test members may be used for HealthFlow, and how many attendance creations are allowed.
2. Record the confirmation reference. Stop here if it is not in writing.

## 2. Prepare a disposable HealthFlow test deployment

1. Create or use a separate test Supabase project (or a local stack). Apply, in order: `20261010090000_organization_ccc_providers.sql`, `20261020200000_prepare_nehfams_connection.sql`, `20261021090000_nehfams_test_validation_and_linkage.sql`. Do **not** apply them to production as part of this test.
2. Set the server-side secret `NEHFAMS_TEST_ATTENDANCE_ENABLED=true` on the **test** edge function only. Confirm it is absent in production.
3. Deploy the NeHFAMS-capable `tier-access` function to the test project only.

## 3. Store credentials securely **[CREDENTIALS]**

1. Sign in to the test deployment as an active platform administrator (`super_admin`).
2. In the CCC settings for the test facility, choose **NeHFAMS** and environment **Test**, enter the expected facility HPN and facility name exactly as NHIA issued them, and enter the API key and secret in the credential fields. Save. Saving disables generation.
3. Confirm: the fields clear after saving, the secret never appears in the browser network tab responses, and nothing appears in function logs. Do not screenshot the form with values in it.

## 4. Validate facility identity and HPN (read-only)

**Step 4a, before touching HealthFlow:** run `scripts/nehfams-hpinfo-shape-check.mjs` once to see the real shape of the `hpinfo` response. It makes one `GET /api/hmis/auth/hpinfo` to the test origin only, reads the credentials from environment variables, prints field names, types and yes/no checks (never values), and refuses production, a missing confirmation flag or missing credentials. The PowerShell snippet that prompts without echo is in the script's header. Pass `--confirm-test-authorized` only with NHIA's written authorization. Exit code 0 means the response matches the documented contract; 1 means it differs (for example different casing); 3 means the request failed. Keep the printed output as protected evidence and compare it with the contract before step 4b.

**Step 4b, in HealthFlow:**

1. Use **Validate saved connection**. This performs one `GET /api/hmis/auth/hpinfo`.
2. Expected: the returned `HPN` and `HPName` equal what you entered; `AuthMode` is `1FA` or `2FA`; `OTACAuthEnabled` is a boolean.
3. Record (redacted, in protected evidence): the exact JSON **casing and types** of every field, and the HTTP status. Compare with the documented PascalCase contract.
4. If the identity differs, or `AuthMode` is `3FA`, or `AuthMode` is `2FA` with `OTACAuthEnabled=false`: **stop**. HealthFlow deliberately blocks these. Ask NHIA how to proceed. **[NHIA]**
5. Optional read-only call: `GET /api/hmis/lovs`. HealthFlow does not depend on it.

## 5. Decide the authentication path

- `1FA` and `OTACAuthEnabled=false`: the request omits `OTAC`. Confirm with NHIA that omission (not an empty value) is accepted. **[NHIA]**
- `2FA` and `OTACAuthEnabled=true`: a four-digit OTAC generated by the NHIS client is required. Use the NHIA-authorized method to obtain it for the test member. **[NHIA]**
- Anything else: not supported by HealthFlow. Stop.

## 6. Select the test member and card type **[TEST MEMBER]**

Use a member NHIA names for testing, with the matching card type (`NHISCARD`: 8 digits; `GHANACARD`: `GHA-#########-#`). Do not substitute a real member.

## 7. Activate the test environment (explicit, local, reversible)

1. Use **Activate test attendance** (platform administrator). It refuses unless the connection was validated for the current credential version within 24 hours and the server flag is on.
2. Confirm that **production** NeHFAMS cannot be enabled: saving the NeHFAMS provider with generation enabled is rejected by the edge function, and the database independently rejects an enabled production NeHFAMS policy.

## 8. Create exactly one test attendance **[NHIA authorization for this step]**

1. Immediately before the request, confirm there are no unresolved ledger rows for the facility.
2. In HealthFlow, use the explicit Generate CCC action for the test member. HealthFlow reserves first, sends one POST, and stores the result.
3. Do **not** retry from the UI, a script or a proxy if the outcome is unclear.
4. Do not save a claim with a blank CCC during this session. (Claim saving no longer auto-generates a NeHFAMS attendance, but avoid the question entirely.)

## 9. Capture sanitized evidence

Record, in protected evidence only: timestamp (UTC), environment, request path and method, request body **keys** (not member values), HTTP status, response top-level keys and the type of each value, `StatusCode`, `StatusMessage`, the HealthFlow ledger row id and its final status. Redact `MemberName`, `MemberPhone`, `DOB`, `HIN`, `UMN`, `AuthID`.

## 10. Verify the outcome in HealthFlow

- **CCC**: five characters, kept as text. If NHIA returns a value with a leading zero (for example `01234`), it must appear unchanged in the response, the ledger `result->ccCode` and any synthetic claim payload.
- **Mapping**: `newCCC` boolean preserved; `AttendanceDate` equals the requested day in `YYYY-MM-DD`; `AttendanceType` recorded as received.
- **Environment label**: the ledger row says `test`. The Generate action shows the test notice and must **not** fill a production claim form.
- **Linkage**: attempting to link this test attendance to a production claim must be rejected by the database. Linkage is exercised with a synthetic production fixture elsewhere, not with this test attendance.

## 11. Exercise error and uncertainty handling (without disrupting NHIA)

Use mocks or a local proxy you control, not live fault injection:

- HTTP 200 with `StatusCode=1`: no CCC is shown; the ledger row becomes `unknown`; a second attempt for the same member and day is refused as unresolved.
- Timeout or dropped connection: the same. Count requests at the proxy: exactly one.
- Malformed or differently-cased response: not accepted as success; row becomes `unknown`.
- Wrong credentials (`401`) during validation: validation fails, nothing activates.
For any `unknown` row, **ask NHIA whether the attendance exists** before reconciling. There is no documented status-lookup endpoint; do not invent one. **[NHIA]**

## 12. Record the outcome

For each step write pass/fail, the evidence reference and any discrepancy from the documented contract (casing, date format, field types, leading zeros, status semantics). Then **disable test activation** and leave production NeHFAMS disabled.

## Needed from NHIA before or during the test

| Item | Why |
|---|---|
| Written authorization for the test origin, accounts, members and number of attendance creations | Step 1 |
| Test API key/secret per authentication mode, test facility HPN and exact HPName | Steps 3-4 |
| Named test members (card type and number) | Step 6 |
| How a 2FA test OTAC is generated without the dev tools | Step 5 |
| Whether `StatusCode=1`, HTTP 400 and HTTP 401 guarantee that no attendance was created | Step 11, reconciliation policy |
| Duplicate behavior: what a second request for the same member and day returns, and what `newCCC=false` means for HealthFlow's cache | Steps 8, 10 |
| A supported way to confirm whether an attendance exists after an uncertain outcome | Reconciliation |
| Whether `AttendanceDate` may carry a time component, and the actual response casing | Parser strictness |
| Handling of 3FA and of 2FA without OTAC | Currently blocked in HealthFlow |
