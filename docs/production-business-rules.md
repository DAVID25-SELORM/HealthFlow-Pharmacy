# HealthFlow Production Business Rules

Version: 2026-08 baseline. These IDs are stable and must be cited by changes that affect the rule.

| ID | Rule | Enforcement | Outcome | Evidence |
|---|---|---|---|---|
| AUTH-001 | A signed-in user must resolve to an active application identity before protected work is available. | `AuthContext`, Auth/role services | Block | `AuthContext.test.jsx` |
| AUTH-002 | Recovery links must work across browsers/devices and invalid or reused tokens fail safely. | `AuthContext`, Supabase recovery flow | Block | Recovery tests in `AuthContext.test.jsx` |
| TENANT-001 | Data access remains scoped to the active organization and branch; selected roles must be assigned to the user. | RLS, `tier-access`, contexts | Block | `tier-access/index.test.js`, tenant tests |
| STAFF-001 | Admin-created staff credentials are preserved exactly; status, role, organization, and branch remain enforced. | `staff-admin`, settings service | Block | `settingsService.staff.test.js` |
| NHIS-001 | CCC/CC code must satisfy current readiness rules before serving/final submission. | `nhisService` | Block | NHIS readiness tests |
| NHIS-002 | Ghana Card-linked CLAIM-it exports use the saved numeric HIN as member number and a blank card serial; ordinary members retain their numeric NHIS number. | `nhisService` | Block | NHIS tests and golden contract |
| NHIS-003 | Pharmacy prescription attachments and verification follow current intake/final-export rules; hospital attachment behavior remains optional unless explicitly required. | `nhisService` | Block/warn by workflow | NHIS attachment tests |
| NHIS-004 | Export date filters use service date, with the documented creation-date fallback only when service date is absent. | `nhisService` | Block invalid periods | NHIS export-period tests |
| NHIS-005 | A valid 5-digit CCC/CC code is required to save or send an NHIS claim from the claim form (Save Details, Send to Dispensary and the correction saves that share it); NHIS-001 and the export check still apply later. The code can be generated through NHIA or typed by hand when generation is unavailable. A user whose CC field is locked (manual claim control, role not permitted to type the code) is not blocked. The point-of-sale NHIS sale has its own rule (NHIS-006). | `Nhis.jsx` (`handleSubmitClaim`), `nhisCccSaveRule` | Block | `nhisCccSaveRule.test.js` |
| NHIS-006 | An NHIS sale at the point of sale requires a valid 5-digit CCC/CC code before it can be completed (the earlier behaviour, where the code was optional and a blank code was left for claims-officer review, is replaced). An admin, super admin, claims officer or branch manager may complete the sale without a code when NHIA is unavailable, but must give a reason of at least 5 characters, which is written into the review claim notes. The active role is authoritative. The sale and the review claim otherwise behave as before. | `Sales.jsx` (`handleCompleteSale`, `buildNhiaReviewClaim`), `nhisPosCccRule` | Block | `nhisPosCccRule.test.js`, `nhisCccPersistence.contract.test.js` |
| NHIS-007 | An "early refill review" (match type `early_refill_review`, 7 or more days of the earlier supply remain), "same medicine code" (`exact_code`, same medicine, fewer than 7 days remain) or "similar active ingredient" (`same_ingredient`, same ingredient under another code such as a different pack size, fewer than 7 days remain) active-medication alert blocks export by default. An organization administrator may allow such claims to be exported for their pharmacy; completion supply and partial supply alerts and every other export blocker still block. The setting is fail-closed (missing or unreadable means blocked), changes are audited in `nhis_early_refill_export_policy_audit`, and each export that releases claims records an audit event. Duplicate NHIS claims are always blocked pending the per-group review: the earlier organization duplicate-export opt-in is retired and no longer read. | `nhisService` (`getNhisExportActiveMedicationBlockers`), `nhisEarlyRefillExportPolicy`, `Nhis.jsx` | Block (administrator opt-in release) | `nhisEarlyRefillExportPolicy.test.js`, `nhisEarlyRefillExportPolicy.contract.test.js`, `nhisService.test.js` |
| NHIS-008 | At the point of sale a CC code is requested from NHIA only by an explicit click on "Generate/Validate CC Code via NHIA", shown to claims staff (admin, super admin, pharmacist, billing, claims officer, records officer, or a user with the claims permission; never an assistant), through the same route as the NHIS claim form: the branch server's existing CC route when the facility runs a local branch server, otherwise the cloud function (which requires claims staff and identifies the facility from the signed-in user). A facility whose branch server is offline has no route and can still type the code. It is never requested as a side effect of selecting a patient, completing a sale or saving a claim. The route identifies the organization and branch itself and refuses non-claims staff. A test-environment attendance, a pending reply, an eligibility error or a code that is not exactly 5 digits never fills the code. An attendance already confirmed for the same member that day is reused, not requested again. Typing the code stays available, and NHIS-006 still applies. When a code is generated here, the attendance details NHIA returned with it (attendance ID, attendance type, new CCC, eligibility start and end dates, attendance date, and the confirmed-attendance status and source) are copied into the NHIS review claim, as the NHIS claim form does, but only while the code in the box is still the generated one, only for a non-test reply for the same member, and only when the attendance date is the sale's service date. The patient record stays the identity of the sale: NHIA's HIN, gender and date of birth fill blanks only (so the claim save never overwrites the patient's HIN), the name is never replaced, and a difference in HIN, date of birth or gender is written into the review claim notes. A typed code carries none of these details. | `Sales.jsx` (`handleGenerateNhiaCcc`), `nhisPosCccGeneration` | Block (explicit only) | `nhisPosCccGeneration.test.js` |
| SCRUB-001 | Duplicate claims are detected before export and one claim can be retained while the duplicate is removed through authorized workflow. | NHIS scrub/export | Block | Duplicate export tests |
| SCRUB-002 | Required member, prescriber, diagnosis, medicine, tariff/G-DRG, attachment, and other issue categories preserve their current severity. | NHIS readiness/scrubber | Block/warn/info | `nhisService.test.js` |
| SCRUB-003 | Active-medication checks exclude the current claim, normalize dose frequency, support Ghana calendar-day partial dispensing, and block remaining full-course coverage. | DB RPCs and NHIS service | Block/warn | Active-medication tests/migrations |
| PRICE-001 | Claim totals, drug prices, tariff prices, and service-line totals use their existing authoritative calculations. | NHIS/pricing services | Block invalid values | Pricing and NHIS tests |
| INVENTORY-001 | Direct serving and normal dispensing preserve transactional stock behavior and permissions. | NHIS/inventory services and RPCs | Block | Serving/inventory tests |
| EXPORT-001 | CXF generation remains parseable, attachment-complete, bounded for large batches, and cannot silently omit requested files. | `nhisService` | Block | CXF and attachment tests |
| RECYCLE-001 | Authorized deletion is recoverable, tenant-scoped, and auditable; permanent deletion requires explicit authorization. | Recycle Bin RPC/service | Block | `recycleBinService.test.js` |
| OFFLINE-001 | Offline installer publication, download permission, signed access, branch registration, and sync remain separately authorized. | Installer release service, branch server | Block | Offline installer/sync tests |
| AUDIT-001 | Security and critical claim actions retain actor, organization, action, and result evidence without exposing secrets or clinical payloads in logs. | Audit service and RPCs | Non-blocking where documented | `auditService.test.js` |

## Change Rule

Do not infer new business behavior from this register. If production behavior is unclear, document the gap and obtain product-owner approval before changing it. Updating a rule requires tests that show the old and approved new behavior, migration impact where applicable, rollback steps, and CODEOWNER approval.
